# Architecture decisions

Short records of decisions that are expensive to reverse or easy to forget. Each states the evidence it rests on; revisit a decision when its evidence changes.

## ADR-001 — Stay a single Next.js application for now (2026-10-27)

**Context.** The long-term vision includes Python, Rust and other services. Today there is one TypeScript app with no server-side compute.
**Decision.** Do not convert to a monorepo or add services until a concrete workload needs one. New top-level directories are added only with working code (`benchmarks/`, `docs/` so far).
**Evidence.** Benchmarks show the simulator is not a bottleneck (ADR-004); pages are 8–27 KB gzipped; there is no persistence or background work yet.
**Revisit when.** A feature needs server-side compute, persistence, a Python ecosystem library, or work that should not block the browser (e.g. large Monte Carlo runs).

## ADR-002 — One numeric contract for every consumer of simulation inputs (2026-10-27)

**Context.** Limits were hand-copied into the share-link decoder and the UI, and the model enforced none: `simulate()` returned `ok: true` with NaN/Infinity totals and accepted negative wear (verified by probing).
**Decision.** `src/lib/sim/contract.ts` owns every limit. The model validates every call and fails closed (including a boolean-only free stop); the decoder, the encoder and the UI read the same limits, and the encoder refuses any state the decoder would reject. The range predicates (`inRange`) are allocation-free; error messages are built only on failure.
**Evidence.** 177 contract cases generated from `LIMITS`. Manual mutation checks (run by hand during development, not automated): removing validation failed 33 cases; removing only the wear check failed 8; a 1 s decoder drift failed the agreement case; removing encoder validation failed 54 tests; removing the free-stop check failed 6. Overhead measured at 0–5 % against `HEAD` in alternating runs; an intermediate closure-based version cost +65–125 % and was rejected after micro-benchmarks located the cost.
**Consequence.** Optimisers and an AI layer can call `simulate()` directly without inheriting UI-only protection.

## ADR-003 — Reproducible experiments with content-addressed identity (2026-10-27)

**Decision.** An experiment is `{raceId, datasetVersion, modelVersion, totalLaps, assumptions, strategies}`; its id is `exp_` + FNV-1a-64 of canonical JSON (sorted keys, non-finite numbers kept distinct). Dataset version is SHA-256 (64-bit prefix) of the canonical race file, computed server-side. `MODEL_VERSION` is bumped when output for a valid input can change; a golden test enforces this.
**Why two hashes.** The id is computed in the browser on every edit and must be synchronous; FNV-1a is deterministic, fast and dependency-free. It is an identifier, not a security primitive. The dataset hash is computed once on the server with `node:crypto`.
**Compatibility.** Share links gained optional `r`/`dv` fields; links created before them still decode (a test pins a real link generated by the published version). A link for another race is rejected; a link from an older dataset version loads with a warning. Limitation: links created before provenance existed carry neither field, so they cannot be checked for staleness or for belonging to another race; they are decoded as-is (an unknown driver is still rejected).
**Not yet.** Experiments are not persisted (no store exists); ids identify, they do not retrieve.

## ADR-004 — No native simulation kernel yet (2026-10-27)

**Evidence.** `npm run bench:sim`: ≈ 380k simulations/s on one core; exhaustive 1–2 stop search (37,296 strategies) ≈ 100 ms; one lab edit ≈ 14 µs.
**Decision.** Keep the TypeScript model as the single source of truth. A Rust (or other) kernel needs a benchmarked workload where TypeScript is the bottleneck, shared test vectors (the golden experiment is the first), and explicit tolerances.
**Hypothesis to test.** Monte Carlo (e.g. 1,000 scenarios × 37k strategies ≈ 37M simulations ≈ 100 s single-threaded) would justify parallelism first (Web Workers / worker threads), and a native kernel only if that is insufficient.

## ADR-005 — Patch security advisories immediately; gate CI on them (2026-10-27)

**Context.** After publication, `next@16.4.0` gained two critical remote-code-execution advisories (GHSA-2464-fhr4-w9xw, Image Optimization API with SVG; GHSA-673q-mjm6-r5xr, `use cache` returning typed arrays) and one high-severity denial-of-service advisory (GHSA-p3m5-59mp-jv5r, Server Actions), all fixed in 16.4.1; `zod <4.6.6` gained a high-severity one (GHSA-mrhx-c7xc-m3w5). They surfaced only because `next build` began failing with `SecurityFatalError`.
**Decision.** Upgrade to `next@16.4.3` / `eslint-config-next@16.4.3` / `zod@^4.6.7` explicitly (not via an opaque upgrade agent), add `npm audit --omit=dev --audit-level=high` to CI, and add Dependabot (weekly npm + Actions).
**Evidence.** Audit: 0 vulnerabilities after upgrade; the audit step exits 1 on the pre-upgrade lockfile. Exposure: `/_next/image` was reachable by default (it returned 200 for a local image in this build even though the app does not use `next/image`); the app does not use `use cache` or Server Actions; whether the 16.4.0 deployment was exploitable was not verified. Reachability alone does not establish exploitability, and was not a reason to delay the upgrade.

## ADR-006 — Generated race registry; the race files are the source of truth (2026-10-27)

**Context.** Race availability was maintained by hand in `repository.ts` (three static imports and a key map) and duplicated in `data/index.json`, which `fetch-data.mjs` wrote but nothing read. Nothing checked that a registered key matched the dataset's declared `id`: registering the Italy file under `2024-01-bahrain` was accepted and served the Italian Grand Prix at the Bahrain URL (verified by probing).
**Decision.** `scripts/generate-race-registry.ts` validates every `data/races/*.json` (JSON, race schema, `id` = filename = route, route-safe filename, no duplicates, no stray files) and generates `src/lib/data/race-registry.generated.ts` (static imports, so no runtime filesystem access and no client bundle change) and `data/index.json` (the single writer; `fetch-data.mjs` no longer writes it). Output is sorted in code-point order. The repository additionally rejects any key/`id` mismatch at load time. A unit test fails if the committed generated files are stale.
**Evidence.** Regeneration left every data file byte-identical (SHA-256 checked), so dataset versions are unchanged. 15 registry tests (failure modes use temporary fixtures, never the bundled data); manual mutation checks: removing the identity check fails 1 test, a hand-edited registry fails 3 tests and `registry:check`.
**Why not runtime discovery.** Reading the directory at runtime would need server-only filesystem access on every request and would not work for client bundles; Turbopack's support for glob imports was not relied on.

## ADR-007 — Nonce-based CSP, which requires rendering every page per request (2026-10-27)

**Context.** Production HTML (audited per page) contains 3–5 inline scripts per page (Next.js RSC flight data and bootstrap, next-themes' anti-flash script), no `<style>` elements, and up to 290 server-rendered `style="…"` attributes. All scripts and assets are first-party.
**Options measured.**
- *Static pages + experimental SRI* (`experimental.sri`, `script-src 'self'`): built in a scratch copy and loaded in Chromium — every inline script was blocked (4–5 violations per page), the app did not hydrate and the theme script did not run. Rejected on evidence.
- *Static pages + `'unsafe-inline'` scripts*: keeps performance but gives little XSS protection. Rejected.
- *Per-request nonce* (chosen): `src/proxy.ts` generates 128 random bits per document request; Next.js stamps the nonce on its scripts, and the root layout passes it to next-themes.
**Policy (production).** `default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; style-src 'self' 'nonce-…'; style-src-attr 'unsafe-inline'; img-src 'self'; font-src 'self'; connect-src 'self'; worker-src 'none'; manifest-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` (+ `upgrade-insecure-requests` when served over HTTPS). The `style-src-attr` exception exists because nonces cannot apply to style attributes. Development adds `'unsafe-eval'` and inline styles (for `next dev` only).
**Zod.** Zod v4 probes `new Function` to decide whether to JIT-compile; under this policy the probe was reported as a violation on the strategy lab. `src/lib/zod-setup.ts` sets `jitless` (zod's documented switch), removing the eval attempt; all 310 unit tests pass unchanged.
**Cost (measured, local, same machine, alternating runs).** Formerly static pages became dynamic: `/` p50 2.0 → 5.5 ms and 478 → 173 req/s single-client (806 → 224 req/s at 8 concurrent); a race page p50 5.5 → 14.5 ms and 176 → 62 req/s (298 → 74 req/s at 8 concurrent). The strategy lab, already dynamic, was unchanged (77 → 86 req/s). Responses are `private, no-store`: no CDN caching of HTML; static assets are unaffected.
**Revisit when.** Traffic makes per-request rendering costly (first: memoise per-race derived data, which is immutable), or Next.js gains static-compatible hashing of inline scripts.

**Re-evaluation (2026-10-28) — a static-preserving alternative, measured but not adopted pending a decision.** A hybrid policy was prototyped in an isolated copy: static pages keep static generation and allow their inline scripts by SHA-256 hashes computed after `next build` from the prerendered HTML; per-request responses (strategy lab, unknown-race 404s) use a nonce plus those hashes. Because unknown URLs are served the *static* 404 page, one policy must fit both, so it uses `script-src 'self' 'nonce-…' <hashes>` **without** `'strict-dynamic'`; next-themes' theme script and injected transition `<style>` are allowed by hash. Measured: zero CSP violations across the same flows as `e2e/csp.spec.ts` (negative control: removing one hash produced a violation); static pages served `s-maxage=31536000` again; throughput 65–90 % of the pre-CSP static build versus 25–30 % for the current design. Costs: the hash manifest is tied to each build (`BUILD_ID` is random and embedded in an inline script, so one hash per page changes on every rebuild) and must be regenerated after every `next build`; the proxy reads it from `.next/` at runtime (portability to hosts that bundle the proxy separately, e.g. Vercel, unverified); `'self'` without `'strict-dynamic'` trusts every same-origin script (acceptable only while the origin serves nothing but build assets); any HTML-rewriting CDN feature would break hashes.

## ADR-008 — A standard-library Python harness for reproducible coding tasks (2026-10-28)

**Context.** Roadmap Milestone 6 calls for bug-injection tasks built from this codebase, with reference fixes and verifiers that reject superficial fixes. That needs a runner, a task format and evidence that each task discriminates; none existed.
**Decision.** `evals/` holds a self-contained Python package (`apexstint_evals`, standard library only; `pytest`/`ruff` for development) and tasks under `evals/tasks/<id>/`. Layers are separate: `spec` (strict `task.toml` validation), `runner` (argv-only subprocess, timeout with process-group kill, output cap, minimal environment), `scoring` (verifier protocol → pass/fail/timeout/error; a verifier that reaches no verdict is never a pass), `harness` (temporary workspace per run), `report` (sorted JSON; SHA-256 digest of everything but runtime). Each task declares **controls**: the reference must pass, and the starter and plausible wrong fixes must fail with exactly the declared checks (`selftest`, run in CI).
**First task.** `move-stop-distance`, a Python port of `moveStop` (`src/lib/sim/model.ts`) with a seeded off-by-one clamp that creates 0-lap stints. Synthetic inputs only, so no dataset licence applies. The verifier runs the candidate in a separate process and judges 13 checks over 30,331 enumerated cases (type and identity are recorded before JSON serialisation; a no-op may return the caller's list, as the TypeScript `moveStop` does); five wrong fixes are rejected, each by different checks; an independently written correct implementation passes; the reference matches a brute-force specification on more than 50,000 inputs.
**Why Python, not TypeScript.** Agent-evaluation tooling and task authors are predominantly Python; the harness has no dependency on the app and runs without Node. The task deliberately ports a TypeScript invariant so the two can be compared.
**Limits.** Not a sandbox: candidate code runs as the current user with filesystem and network access, can read ancestor processes' environments through `/proc`, and can leave processes running after a normal exit (only a timeout kills the process group) (`evals/README.md`, "Security limits"). Untrusted code must run inside a disposable container or VM, never from a session holding credentials.
**Review fixes (2026-10-28).** An adversarial review found four false passes; three were fixed with regression tests: tuple results (now rejected), ambiguous `--candidate` names (replaced by `--control` / `--candidate-dir`, abbreviations rejected) and an unused `entry_file` (now passed to the verifier and required by validation). The fourth — a candidate that loads the hidden reference — needs the container runner.
**Evidence.** 108 pytest tests (Python 3.12 locally; 3.11 runs only in CI); manual mutation checks: removing the list-type check fails 2 tests; removing the new-list check fails 1; running commands outside their own process group fails 2 runner tests (the grandchild survives the timeout); passing the caller's environment through fails the canary-variable test.

## ADR-009 — Rust: a bounded proposal, not yet implemented (2026-10-28)

**Status.** Proposed. No Rust code exists: no Rust toolchain is installed in the development environment, and installing one was out of scope for this change.
**Candidate component.** The exhaustive strategy search (`search.exhaustive` in `benchmarks/sim-bench.ts`): every legal 1- and 2-stop dry strategy for a race, returning the best.
**Contract.** Input: `totalLaps` (integer, `LIMITS`-checked), `Assumptions` (base lap, pit loss, per-compound model, all validated against `contract.ts` limits), stints start on new tyres with charged stops. Output: the minimum total (seconds), the strategy that achieves it (ties broken by the TypeScript enumeration order), and the number of strategies evaluated. Invalid input is a typed error, never a NaN result.
**Complexity, and why a straight port is the wrong first step.** Today every candidate is simulated lap by lap: 37,296 strategies × 57 laps ≈ 2.1M lap-time evaluations for Bahrain (≈ 100 ms measured). But a stint's cost depends only on (compound, length) on new tyres, so a table of `C × N` stint costs (3 × 57 entries) built once makes each strategy 2–3 additions: O(C·N) + O(C³·N²) instead of O(C³·N³). That algorithmic change applies equally to TypeScript and should be measured there first; a Rust kernel is justified only if the table-based search, or a future Monte Carlo workload (ADR-004), is still a bottleneck.
**Why an independent implementation is still useful.** A second implementation from the written contract (not a transliteration) is a differential test of the TypeScript model: disagreements expose under-specified semantics such as rounding, tie-breaking and cliff boundaries.
**Correctness comparison.** Golden vectors exported from the TypeScript `simulate` (assumption sets × races, including 1-lap and 2-lap races, cliff onsets at stint boundaries, zero degradation, maximum limits); totals must agree within 1e-6 s before rounding, and the chosen strategy must match unless two totals differ by less than that tolerance.
**Performance comparison.** Same inputs, same machine, alternating runs, median of runs; report TypeScript naive, TypeScript table-based and Rust table-based separately, with the environment recorded as in `benchmarks/README.md`. No speedup is claimed without those numbers.
**Next bounded step.** (1) Pin a toolchain (`rust-toolchain.toml`) and add it to CI; (2) `scripts/export-search-vectors.ts` writes the golden vectors; (3) `native/strategy-search/` crate with typed input/error types, unit and boundary tests, and a vector-equality test; (4) a dependency-free benchmark binary. No integration into the web app.
